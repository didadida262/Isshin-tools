# 当接口签名无法离线复刻：一次从「破解算法」到「借用签名者」的思路转向

## 起因

一个自用的抖音下载工具，原本工作得很好：手动填入几个关键 cookie 字段，就能拉取「我喜欢的」视频列表并批量下载。连续用了几天之后，接口开始稳定返回 403，一条数据也拉不到。

但有个耐人寻味的现象：从浏览器开发者工具里复制出来的 cURL 命令，粘到终端里执行，**能正常拿到数据**。

同样的 cookie、同样的接口、同样的机器，一个通一个不通。这个矛盾就是整个排查的入口。

一次失败的尝试也值得先提一句：有人试着把抓包得到的 URL 和请求头整体复用到代码里，确实能拉到第一页数据，但每次「加载更多」都得重新抓一次包。这个现象后面会看到，其实精准地指向了根因。

## 第一步：把猜测变成对照实验

一条完整的 cURL 里有几十个可疑变量——一大串 cookie、四五个 `bd-ticket-guard-*` 请求头、`a_bogus`、`msToken`、`verifyFp`、`timestamp`、`x-secsdk-web-signature`。凭直觉挑一个去试，命中率很低，而且失败了也不知道是这个变量无关，还是它和别的变量有耦合。

更可靠的做法是**从一个已知成功的请求出发做减法**，一次只改一个变量，观察它何时开始失败。成功的基线比失败的基线有价值得多：失败有无数种原因，而在成功基线上做的每一次改动，结果都能直接归因。

几轮实验后，结论收敛得很干净：

| 改动 | 结果 |
| --- | --- |
| 删掉所有 `bd-ticket-guard-*` 请求头 | 成功 |
| 删掉 `x-secsdk-web-signature` 和 `timestamp` | 403，`Signature Not Found` |
| 保留签名，只把 query 里的 `max_cursor=0` 改成其他值 | 403，`Sign Invalid` |

第一行排除了一大片干扰项——那几个看起来最像风控的请求头其实无关紧要。

真正的关键在后两行，而且**两条报错信息不同，这个区别是整件事的核心**：

- `Signature Not Found` 说明这个参数现在是**强制**的。服务端在找它，没找到就直接拒绝。
- `Sign Invalid` 说明签名**绑定了完整的 query 字符串**。签名本身没动，只改了一个业务参数，校验就失败了。

> 排查过程中踩了个和主线无关但很能浪费时间的坑：`curl -b @文件` 会被 curl 理解成 cookie jar 的路径，而不是把文件内容当作 cookie 字符串。这导致其中一轮实验返回 200 空 body，一度被误判成「账号被软封、强制登录」。换成用脚本显式构造 `Cookie` 请求头之后，实验结果才干净可信。**当实验结论违反直觉时，先怀疑实验装置本身。**

## 这组结论解释了全部现象

三个原本孤立的现象，用同一个原因就能全部串起来：

**为什么旧代码突然失效。** 平台在这个接口上新增了 `x-secsdk-web-signature` 强制校验，而旧代码只实现了 `a_bogus`。`a_bogus` 并没有失效，它只是从「充分条件」降级成了「必要条件之一」。

顺带纠正一个很自然的误判：这不是「下载太频繁被封」。是服务端策略升级，与账号行为无关。误判成封禁的话，接下来会去做限速、换 IP、加随机延迟——全都是无用功。**归因错了，后面所有努力都会浪费在错误的方向上。**

**为什么粘贴 cURL 能成功。** 那条命令里携带着真实浏览器的 SDK 为**那一个精确 URL** 生成的签名。它是一份正确的答案，但只对那一道题有效。

**为什么「加载更多」特别麻烦。** 这是同一个原因的必然结果。复用抓包得到的 URL，意味着复用了那个绑定死的签名，所以只有抓包当时那一页（`max_cursor` 恰好等于当时的值）能拉到。翻页必须修改 `max_cursor`，而任何修改都会让签名失效。

这一点值得强调：那个方案不是「不够完善」，而是**在原理上就不可能支持自动翻页**。它每翻一页都需要一次人工抓包，因为每一页都需要一个新的签名，而签名的生成能力不在自己手里。识别出「这是原理性上限，不是实现质量问题」，才能果断放弃这条路，而不是继续投入去优化它。

## 关键决策：不复刻算法，改成借用签名者

根因清楚之后，摆在面前有两条路。

**第一条：离线复刻签名算法。** 这是最直觉的路，也是我否掉的那条。

`a_bogus` 曾被社区逆向过，看起来有先例。但 `x-secsdk-web-signature` 出自平台的安全 SDK（重度混淆，核心逻辑在 WASM 里），而且从 cookie 里能看到 `__security_mc_1_s_sdk_sign_data_key_web_protect`、`__security_mc_1_s_sdk_cert_key` 这类字段——它与设备证书绑定，每个请求重新签发。

即使今天逆出来了，对方推一次版本就全部作废。这是一场没有终点的军备竞赛，而且投入产出比极差：这只是一个自用小工具，不值得押上无限期的维护成本。

**第二条：换个位置发请求。**

转机来自一个观察：这个 SDK 是通过**替换 `window.fetch`** 来加签的。签名不是在某个特定的业务函数里生成的，而是在网络层统一注入的。

这个观察改变了问题的性质。如果请求是从一个真实的页面**内部**发出去的，它就会被自动签名——任意 URL、任意翻页参数，而且永久有效，因为用的始终是对方自己最新的那份签名逻辑。

于是「破解一个加密算法」这个问题，被替换成了「让请求从正确的位置发出」。后者的难度和前者根本不在一个量级上。

这类转向在工程上很常见，值得单独记住：**当一个问题的正面解法需要无限期维护时，先回头检查问题的定义是不是可以换一个。** 与其复制能力，不如借用能力。

## 动手之前，先用最低成本验证核心假设

新方案的成立与否，全部押在一个尚未验证的假设上：SDK 的 hook 会不会给**我们自己构造的**任意 URL 加签？

这个假设很容易被忽略，但它并不显然。完全有可能 SDK 只对自己业务代码发出的请求加签（比如通过内部封装的请求客户端、或校验调用来源）。如果是那样，整个设计从根上就不成立。

所以第一行产品代码都还没写之前，先做验证：用 Chrome DevTools Protocol 驱动一个真实浏览器打开目标站点，在页面上下文里执行一句最朴素的 `fetch(...)`，并且**故意填一个抓包里从未出现过的翻页游标**。

返回 200，带完整数据。一次实验同时证明了三件事：

1. hook 确实生效，我们的请求会被签名；
2. 任意 URL 都会被签名，不校验调用来源；
3. 翻页可行——这正是原方案做不到的那件事。

假设验证通过之后再动工，剩下的就只是工程实现问题了。

> 这一步也卡了一会儿：CDP 始终连不上本地调试端口，最后发现是系统级 HTTP 代理连 `localhost` 的请求都要拦截，脚本里得显式绕开代理。**在排查中，工具链本身也是变量。**

## 落地方案

架构上只有一个核心点：**隐藏一个 WebView 常驻目标站点，让它成为所有需要签名的请求的出口。**

```
┌──────────────┐   派发请求    ┌──────────────────┐
│  应用主进程   │ ───────────▶ │  隐藏 WebView     │
│              │              │  (目标站点页面)    │
│              │ ◀─────────── │  fetch 已被 SDK   │
└──────────────┘   返回结果    │  替换 → 自动加签  │
       │                      └──────────────────┘
       │ 直连（无需签名）              │
       ▼                              │ 取 cookie
┌──────────────┐                      │
│  CDN 下载     │ ◀────────────────────┘
└──────────────┘
```

几个设计取舍：

**通信方式。** 主进程通过在页面里执行脚本来派发请求，再轮询取回结果。这里没有用框架自带的 IPC 机制，因为那需要给一个外部域名授予 IPC 权限——为了一个通信通道扩大信任边界，不划算。

**下载路径不走 WebView。** 媒体文件的 CDN 地址不需要签名，只需要 cookie。所以下载仍然走主进程的 HTTP 客户端直连，只是从 WebView 里取出 cookie。签名通道只承载真正需要签名的 API 请求，两条路径职责分明。

**登录也搬进 WebView。** 这是架构带来的额外收益，而且收益比预想的大。原来要手动填一堆 cookie 字段，现在直接在 WebView 里扫码登录。更重要的是，session 续期、验证码、风控挑战全部变成了 WebView 自己的事情，应用层完全不需要关心——**这些原本都是需要单独实现和长期维护的功能，现在它们消失了，不是被解决，而是不再属于我们的问题。**

## 设计正确不等于能跑起来

方案跑通之前还有两个只有真正运行才会暴露的问题。这部分往往比架构设计更耗时间。

**问题一：请求静默卡死。**

第一次联调，请求发出去之后毫无反应，直到超时。

原因在于我设计的取结果协议有歧义：「请求还在进行中」和「请求已经丢失」这两种状态，返回值都是「暂无结果」。主进程无法区分，只能一直等到超时。

而请求确实会丢失。目标站点首次访问时会先加载一个风控挑战页，计算出校验 cookie 后**重新加载**进真正的页面。这次重载会连带销毁页面里所有在途的请求和状态。如果请求恰好在这个窗口发出，它就凭空消失了。

两处修复：

- 协议改成显式状态机，明确区分「进行中」「已完成」「已丢失」。主进程识别到「已丢失」就自动重发。
- 「页面就绪」的判定加严。原来只要求「`fetch` 已被 SDK 替换」，现在额外要求「文档在一段时间内没有再次跳转」——只有稳定的页面才值得托付一个请求。

这里有个通用教训：**协议设计上，「未完成」和「已失败」必须可区分。** 把两者合并成同一个返回值，会让所有故障都退化成超时，而超时是信息量最低的一种错误——它只告诉你没成功，不告诉你为什么。

**问题二：时序假设过于乐观。**

加上诊断日志后，看到了真实的启动过程：

```
signed=false readyState=complete   ← 风控挑战页，SDK 尚未介入
（窗口被显示出来）
signed=true  readyState=loading    ← 跳转进真实页面，SDK 接管 fetch
ready after 60335ms
GET /...  -> HTTP 200, 5650ms      ← 签名请求成功
```

冷启动穿过风控挑战需要约 60 秒，而原本设定的超时是 75 秒——几乎压线，稍有波动就会失败。放宽之后，cookie 预热完成的后续启动只需 14 秒，请求耗时也从 5.6 秒降到 0.8 秒。

同时暴露一个体验问题：原本的逻辑是「页面加载慢就把 WebView 显示出来让用户处理」，但这条逻辑对后台静默探测也生效，于是用户只是打开工具，一个浏览器窗口就莫名弹到面前。改成按请求来源分三档：

| 请求来源 | 显示策略 | 理由 |
| --- | --- | --- |
| 用户点击登录 | 立即显示 | 用户就是要登录 |
| 用户触发的列表 / 操作 | 仅在卡住时显示 | 卡住通常是验证码，需要用户介入 |
| 后台状态探测 | 永不显示，且快速放弃 | 用户没要求，不该打扰，也不该让界面长时间转圈 |

**同一个「显示窗口」动作，是帮助还是打扰，完全取决于用户是否预期它发生。** 这类判断没法靠通用超时值解决，只能显式区分调用意图。

## 代价

这个方案不是没有成本，说清楚才算完整：

- **吞吐下降。** 所有签名请求串行经过同一个 WebView，无法像直连那样并发。
- **冷启动慢。** 依赖目标页面正常加载，首次有几十秒等待。
- **依赖仍然存在，只是换了位置。** 对方修改页面结构或 hook 机制，方案仍会失效。

但依赖的**性质**变了，这是关键区别。原来依赖的是「签名算法保持不变」——这是对方主动、频繁、且有动机去改变的东西。现在依赖的是「页面能正常加载、SDK 通过替换 `fetch` 加签」——这是对方架构层面的稳定特征，改动成本高、频率低。

对方升级加密算法时，这个方案毫无感觉。这就是它值得的地方。

## 可以复用的几点

1. **从成功的基线做减法，而不是从失败的基线做加法。** 成功基线上的每次改动都能直接归因，失败基线上的每次尝试都可能有多个原因。
2. **不同的错误信息是免费的情报。** `Signature Not Found` 和 `Sign Invalid` 的区别，直接指出了「参数强制」和「绑定 query」两个独立结论。
3. **区分「实现不完善」和「原理性上限」。** 前者值得继续优化，后者必须换方案。看清这一点才能果断放弃沉没成本。
4. **正面解法需要无限期维护时，回头检查问题的定义。** 复刻能力往往比借用能力难几个量级。
5. **动手前用最低成本验证核心假设。** 找出方案里那个「如果不成立，一切白搭」的前提，先单独验证它。
6. **归因错误的代价是全部后续努力。** 把策略升级误判成账号封禁，会让人在限速和换 IP 上白忙很久。
7. **排查时，工具链本身也是变量。** cURL 的参数语义、系统代理，都曾让实验结论失真。
8. **协议里「未完成」和「已失败」必须可区分。** 否则所有故障都退化成超时，而超时几乎不携带信息。
